# Project 3: FieldVoice

Shared context in `00-shared.md` (S1-S14). Repository name: `fieldvoice`.

## 1. Goal and final deliverable

A Python pipeline that converts spoken inspection readings into schema-validated records, whose center of gravity is **measurement, not the feature**. The project's claim is not "I built a voice thing"; it is "I built an evaluation harness with pre-registered hypotheses, confidence intervals, a baseline the model had to beat, and a held-out split the prompt never saw, and here are the numbers."

Final deliverable: public repo, four-command CLI, a committed and checksummed evaluation dataset, published result tables with intervals, and an offline mode running a self-quantized local model with a benchmark.

Headline README numbers: utterance count and speakers, numeric-token error rate with and without keyterm boosting (with interval), extraction F1 versus a regex baseline on a frozen split, and local-model throughput and memory across quantization levels.

Motivating use case, stated plainly as motivation and not as deployed practice: readings are taken gloved, hands occupied, at height, under hearing protection, often with no connectivity, and are transcribed from paper to spreadsheet hours later, where every transcription is an opportunity to transpose a digit.

## 2. Existing state

Greenfield. The developer has Python and async experience (a Discord bot with MySQL) which transfers directly to the streaming client. New: audio processing, speech APIs, evaluation methodology, pydantic, FastAPI, llama.cpp, quantization. See S2.

## 3. Required architecture

A library plus a thin CLI, with a swappable provider boundary at both the speech and the extraction layer so that cloud and local paths are the same code path with different adapters.

```
fieldvoice/
  src/fieldvoice/
    audio/       loading, resampling, active-speech detection, noise mixing
    stt/         base.py (Protocol), deepgram.py, offline.py
    normalize/   spoken-number and unit normalization
    extract/     base.py (Protocol), regex_baseline.py, llm.py, schema.py
    validate/    physical plausibility rules
    eval/        metrics, bootstrap, grid runner, report emitter
    serve/       FastAPI app (offline mode)
    cli.py
  data/
    utterances/  wav files (committed; see §4.1 on size), manifest.json
    noise/       git-ignored; fetch script + checksums
  eval/
    preregistration/   committed before each grid run
    results/           committed result tables and plots
  tests/
  Dockerfile
```

Provider boundary:

```
audio ──▶ SttProvider ──transcript──▶ Extractor ──▶ Reading (pydantic) ──▶ Validator ──▶ record | review
             │  deepgram                │  regex_baseline
             └─ offline (local)         └─ llm (cloud or local)
```

Every stage is independently evaluable. That is the architectural requirement: the evaluation harness must be able to hold one stage fixed and vary another, which is why extraction is evaluated on *real STT output*, not on clean reference text.

## 4. Major components

### 4.1 Evaluation dataset

The most important deliverable and the first one built.

- ~200 utterances covering location identifiers, decimal thickness readings, units, indication flags, and a set of realistic malformed or self-corrected utterances ("CML A-12, point three one two, no wait, point three two one").
- Three speakers: the developer plus two volunteers, with their consent recorded in the repo. Speaker identity is a column so per-speaker results can be reported.
- Recorded with any consumer recorder at 16 kHz mono WAV. No studio setup.
- Vocabulary is **synthetic and generic**, derived from public terminology, never from an employer's forms or nomenclature (S10).
- Three conditions: quiet, and two mixed noise levels using a public industrial-noise dataset (DEMAND, Zenodo, CC BY-SA). Mixing is done at stated SNRs computed as RMS over active-speech segments, not over the whole file, and the mixing function is unit-tested by round-tripping a known-SNR construction.
- `manifest.json` holds per-utterance ground truth (verbatim transcript, and the structured record it should yield), a SHA-256 per file, speaker, condition, and split assignment.
- **Split assignment is frozen before any prompt work**, with a committed seed. The held-out split is never used during prompt development. A test asserts the split hash has not changed.

Size: 200 × ~4 s × 16 kHz × 16-bit ≈ 25 MB for the clean set. Committed. Noise-mixed variants are generated by script, not committed.

### 4.2 Spoken-number normalization

Without this, numeric accuracy cannot be computed at all, because the transcript says "point three one two" and the truth is `0.312`.

A deterministic normalizer handling digit-sequence reading, decimal words, "oh"/"zero", fractional forms, unit words, and location identifiers of the form letter-dash-number. Hand-written, table-driven, with an exhaustive unit-test table. This is one of the components named in `AI-USAGE.md` as hand-written (S7): it is small, it is the kind of thing an LLM writes plausibly and subtly wrongly, and it is the foundation under every published number.

### 4.3 Metrics

- **WER** via `jiwer`, standard normalization, reported for context.
- **Numeric-token accuracy**, the headline metric: of the tokens that carry a number (location IDs and readings), the fraction recovered exactly after normalization. A single transposed digit is a full error. This is the metric that matters for the use case and it is stricter than WER.
- **Per-field extraction F1** with a per-field error taxonomy (decimal word confusion, location-ID normalization, unit mismatch, hallucinated field, dropped field).
- All three with percentile-bootstrap 95% intervals per S9.

### 4.4 Speech provider

Deepgram streaming over WebSocket, with keyterm boosting for the domain vocabulary. Note that the boosting parameter name differs by model generation (`keywords` on older models, `keyterm` on the current generation); the adapter reads it from config and the README states which model and parameter were used.

Streaming is exercised file-paced (audio fed at wall-clock rate) so that time-to-first-transcript and interim-to-final latencies are meaningful. A reconnect-and-backoff state machine is implemented and unit-tested against a **fake transport object**, not against a mock server. One manually induced disconnect during a live run is recorded in the README as a qualitative check. Building a protocol-accurate mock Deepgram server is explicitly out of scope; it was identified in review as a scope trap.

Cost control: the entire dataset is ~15 minutes of audio; a full grid run is a few dollars. A hard cap on API spend is enforced in the runner (count seconds before sending, refuse above a configured budget) and the README publishes the actual spend.

### 4.5 Extraction

Two extractors behind one Protocol:

1. **Regex baseline.** Deterministic, built from the normalizer. It exists so the LLM has to earn its place. If the LLM does not beat it meaningfully, that is a publishable finding and the README says so.
2. **LLM structured extraction.** A pydantic model as the schema, JSON output, prompt and few-shot examples versioned in the repo with the prompt hash recorded in every result row.

Both are evaluated on **real STT hypothesis transcripts**, not on reference text, so the measured F1 includes upstream error propagation, which is the honest number.

### 4.6 Physical validation

Rules independent of the model: reading below nominal minus tolerance, reading above nominal, implausible change versus the previous reading for the same location, unit mismatch, unknown location identifier. Violations route to review rather than being silently corrected.

A `--confirm` flag requires explicit reviewer sign-off before any record is written; the README states clearly that high-confidence records are written without confirmation when the flag is absent, because an earlier description of this design overstated the safety property.

### 4.7 Pre-registered evaluation grid

Before the main run, commit `eval/preregistration/<date>-<name>.md` containing: the factors (model, boosting on/off, noise condition), the primary metric, the decision rule, the minimum difference considered meaningful, and the sentence that will be published if the result is null.

The grid runner emits a tidy result table (one row per utterance × condition) plus aggregate tables with intervals. Everything is regenerated by one command from the committed manifest.

**A null result is an expected outcome and is published as one.** Keyterm boosting may not move numeric accuracy measurably; quantization levels on a small model may be within noise. The pre-registration is what converts that from an embarrassment into evidence of method.

### 4.8 Offline mode

The differentiating half for the applied-AI target postings, whose stated duties are profiling, benchmarking, and quantization on constrained devices.

- Convert a small open-weight instruct model (Qwen2.5-1.5B-Instruct, Apache-2.0, is the reference choice) from safetensors to F16 GGUF using llama.cpp's conversion script, then quantize to three levels (Q4_K_M, Q6_K, Q8_0), with and without an importance matrix computed from the project's own transcripts. **The developer performs the conversion and quantization**; downloading pre-quantized files and timing them is not the claim and would not survive scrutiny.
- Benchmark on the developer's laptop: prompt and generation throughput, time to first token, peak working set. Median of 10 runs, hardware and build flags stated (S6).
- Report extraction-F1 retention per quantization level on the held-out split, with intervals.
- One genuine tuning experiment: thread count sweep and prompt-cache reuse, with a before/after table and an explanation of which was the binding constraint.
- A FastAPI service exposing the offline path, with a test that asserts **zero outbound network calls** (socket-level assertion, not a mocked client) so the privacy claim is verified rather than described.

Local STT is **not** in scope. The offline mode covers extraction only; the README states this boundary explicitly rather than implying an end-to-end offline pipeline.

### 4.9 CLI

Four commands plus the service:

```
fieldvoice eval-stt      --grid eval/preregistration/<file>.md
fieldvoice extract       --input <wav|txt> [--provider deepgram|offline] [--confirm]
fieldvoice validate      --records <jsonl>
fieldvoice eval-extract  --split held_out --extractor regex|llm --quant <level>
fieldvoice serve         --offline
```

Recording is done with any external recorder; there is no `record` command. Live microphone capture exists as a single documented demo script, not as tested library surface.

## 5. Data models and interfaces

```python
class Reading(BaseModel):
    location_id: str          # normalized, e.g. "A-12"
    thickness_in: Decimal     # Decimal, never float
    unit: Literal["in", "mm"]
    indication: bool
    confidence: float
    source_transcript: str
    prompt_version: str | None

class Utterance(BaseModel):
    id: str; path: Path; sha256: str
    speaker: str; condition: Literal["quiet", "snr_high", "snr_low"]
    split: Literal["dev", "held_out"]
    truth_transcript: str; truth_reading: Reading

class SttProvider(Protocol):
    async def transcribe(self, audio: AudioSource, *, keyterms: list[str]) -> SttResult: ...

class Extractor(Protocol):
    def extract(self, transcript: str) -> ExtractionResult: ...
```

`SttResult` carries the hypothesis text, word timings when available, and latency marks (first byte, first interim, final). `ExtractionResult` carries the parsed `Reading` or a structured failure, plus token counts and wall time.

Result rows are written as JSONL with the full provenance needed to regenerate any table: manifest hash, split hash, prompt hash, model id, quantization level, git commit.

## 6. Dependencies

`pydantic`, `httpx` + `websockets` (Deepgram streaming), `jiwer`, `numpy`, `soundfile`, `scipy` (resampling/filtering only), `fastapi`, `uvicorn`, `typer`, `matplotlib`, `python-dotenv`. LLM client per provider choice. Dev: `pytest`, `pytest-asyncio`, `hypothesis`, `ruff`, `mypy`.

External, not Python packages: llama.cpp built in WSL2 (`llama-quantize`, `llama-bench`, `llama-imatrix`, `convert_hf_to_gguf.py`), the DEMAND noise dataset (fetch script with checksums; not committed).

`mypy --strict` is realistic here and is applied to the whole package; unlike Flightcheck there is no DataFrame-heavy code.

## 7. Implementation phases

**Week 1 — dataset and normalizer.**
Write the utterance script covering the vocabulary and the malformed cases. Record three speakers. Trim, resample, checksum, write the manifest, freeze the split with a committed seed. Implement the spoken-number normalizer with its exhaustive test table. CI green. This week produces no model call at all, deliberately: the measurement instrument is built before anything is measured.

**Week 2 — metrics and noise.**
WER and numeric-token accuracy implementations. Percentile bootstrap with its closed-form unit test (S9). Active-speech RMS noise mixing with a round-trip test. Fetch script for DEMAND with checksums. First result: baseline numeric accuracy on quiet audio using a single default provider configuration.

**Week 3 — streaming provider and pre-registration.**
Deepgram adapter with keyterm boosting, file-paced streaming, latency marks. Reconnect/backoff state machine with fake-transport tests. Spend cap. Write and commit the pre-registration for the main grid. Run the grid. Publish the tables with intervals. **Tag `v0.1`** — at this tag the project already answers the Deepgram application form's question with measured numbers, which is the earliest resume value in this project.

**Week 4 — extraction and validation.**
Regex baseline from the normalizer. Pydantic schema. LLM extractor with versioned prompts. Evaluate both on real STT hypotheses over the frozen held-out split. Per-field error taxonomy. Physical-plausibility validator and `--confirm`. 80+ tests green. **Tag `v0.5`.**

**Week 5 — quantization.**
Build llama.cpp in WSL2. Convert the chosen model to F16 GGUF. Quantize to three levels, with and without an imatrix built from the project's own transcripts. Benchmark throughput, TTFT, and peak working set, median of 10, hardware stated. Measure F1 retention per level on the held-out split.

**Week 6 — offline service and tuning.**
FastAPI offline path. Zero-outbound-calls socket-level test. Thread-count sweep and prompt-cache experiment with a before/after table and an analysis of the binding constraint. Dockerfile, built in CI.

**Week 7 — publication and close.**
README as an evaluation report per S5. Result plots. Demo script and a short recorded walkthrough. ADRs, `AI-USAGE.md`. Draft the application-form answer from the published numbers. **Tag `v1.0`.**

Post-v1.0 stretches, not part of the estimate and not claimed before they exist: a LangGraph or similar agentic orchestration over the pipeline; a LoRA fine-tune of the extractor with a proper comparison against the prompted baseline.

## 8. Testing and validation

| Layer | Tool | What it must prove |
| --- | --- | --- |
| Unit | pytest | Normalizer over an exhaustive spoken-number table |
| Unit | pytest | Bootstrap against a closed-form interval; WER against hand-computed examples |
| Unit | pytest | Noise mixing achieves the requested SNR on a constructed signal |
| Unit | pytest (fake transport) | Reconnect/backoff state machine transitions |
| Contract | pytest | Manifest integrity: every file's SHA-256 matches; split hash unchanged |
| Integration | pytest | End-to-end on three committed fixture utterances with a recorded provider response |
| Privacy | pytest | Offline service makes zero outbound socket connections |
| Reproduction | manual | Every published table regenerates from the manifest with one command |

Provider responses for integration tests are recorded fixtures, so CI never calls a paid API.

## 9. Deployment and setup

No hosted deployment. `uv sync`; `DEEPGRAM_API_KEY` in `.env` for cloud paths; `make fetch-noise` for the noise dataset; WSL2 with a built llama.cpp and a converted model for offline paths (documented, with the exact conversion and quantization commands).

The Dockerfile packages the offline path only, so a reviewer can run the local-model service without the developer's WSL2 setup. CI builds it; publishing an image is optional.

## 10. Known risks and unresolved decisions

| Risk | Handling |
| --- | --- |
| **Null results across the board** (boosting and quantization differences within noise) | Pre-registration with the null sentence written in advance (S9). Report it and explain the power limitation. This is the single most likely outcome and the plan is built to survive it |
| Two volunteer speakers may not materialize | Fall back to one speaker, state it, and report per-condition rather than per-speaker results. Do not fabricate speaker diversity |
| Quantization differences need more than 60 held-out cases to detect | State the detectable effect size given N in the pre-registration, before running |
| llama.cpp build or conversion fails in WSL2 | Week 5 is the named risk week. Fallback: report cloud-only results and state that the offline mode is future work. Do not substitute pre-quantized downloads and call it quantization work |
| API cost overrun | Hard spend cap in the runner; published actual spend |
| Volunteer consent and voice data | Written consent committed; no PII in transcripts; speakers identified by pseudonym |
| Scope creep into agents or fine-tuning | Both are post-v1.0 and are not claimed until they exist |

**Unresolved:** which LLM provider for the cloud extractor (cost and structured-output support decide it; either is acceptable, the prompt and schema are portable); exact model for the offline path (Qwen2.5-1.5B-Instruct is the reference, subject to a license check at week 5); whether per-speaker reporting survives if only one speaker records.
